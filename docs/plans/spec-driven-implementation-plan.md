# Spec-Driven Implementation Plan

## Purpose

Use specs and policy tests to keep the AI Infrastructure Fund trading system auditable, advisory-only, and implementation-safe as the repo grows.

The system is local-first, advisory-only, and cloud-model-assisted via Azure AI Foundry. Cloud models may help classify, extract, summarize, review, and explain, but deterministic scoring, backtests, constraints, and target weights must remain reproducible and auditable.

The guiding principle is:

LLMs interpret evidence and explain recommendations. Deterministic code computes signals, risk, backtests, constraints, and target weights.

## AGENTS.md Policy

Keep `AGENTS.md` short. It should enforce non-negotiables and point agents to the detailed specs.

Before implementing fund-dashboard work, read:

- `docs/specs/0008-model-routing-and-audit.md`
- `docs/specs/0009-evaluation-harness.md`
- `docs/specs/0010-repo-patterns-architecture.md`
- `docs/specs/0011-implementation-roadmap.md`
- `docs/specs/0012-data-architecture.md`
- `docs/specs/0013-llm-routing-and-governance.md`
- `docs/specs/0014-risk-monitoring-and-incidents.md`

Hard rules:

- No live order placement or broker execution endpoint.
- Manual buy/sell entry is allowed only as a local trade journal, paper-trade record, or completed-trade record. It must not transmit orders.
- LLMs may extract, summarize, classify, review, and explain.
- Deterministic code owns scores, risk, backtests, constraints, and target weights.
- Business logic must not hard-code model names; use `config/model_profiles.yaml`.
- Cloud model calls must respect data-class routing rules.
- Every recommendation must include evidence IDs, model run IDs, signal bundle ID, target weights ID, and advisory-only labeling.
- `TargetWeights` must be generated by portfolio code, not directly by an LLM.
- Private paid reports and secrets must not be committed.
- Any deviation from the specs must be called out explicitly before implementation continues.

Before finalizing a change:

- Run unit tests for touched modules.
- Run architecture policy tests.
- Report which spec clauses were implemented and which remain pending.

## Make The Plan Enforceable

Turn architecture rules into tests:

- Test that no order, execute, or broker endpoint exists.
- Test that trade-entry endpoints are journal-only and cannot call broker, route, submit, or execute modules.
- Test that signal and portfolio modules do not call LLM clients.
- Test that model names only appear in `config/model_profiles.yaml` and tests.
- Test that every `RecommendationArtifact` requires `evidence_ids`, `signal_bundle_id`, `model_runs`, and `advisory_label`.
- Test that `TargetWeights` cannot be constructed from raw LLM output without deterministic validation.
- Test that fallback behavior exists when LLM calls fail.
- Test that backtests require point-in-time dataset snapshots and availability timestamps.
- Test that stale, quarantined, unlicensed, or incident-frozen data suppresses affected recommendations.

Instructions guide the implementation; tests constrain it.

## Layered Control System

Use a layered control system for all implementation work:

1. `AGENTS.md` for hard rules and required spec-reading instructions.
2. Repo-local skills for repeatable workflows once the patterns stabilize.
3. Explicit subagents for parallel review and verification.
4. Tests and architecture policy checks as the real enforcement layer.
5. CI and non-interactive Codex runs later for repeatable review.

Do not rely on Gmail or Calendar plugins for this repo. They may exist in the environment, but they are irrelevant except for scheduling or planning outside the codebase.

## Subagent Review Protocol

Codex subagents are not automatic. Ask for them explicitly after each implementation phase:

```text
After implementing this phase, use parallel subagents:
1. spec-trace reviewer: verify the diff against AGENTS.md and docs/specs.
2. test-gap reviewer: find missing unit, integration, and evaluation tests.
3. architecture-policy reviewer: check deterministic/LLM boundary, model-name hardcoding, artifact contracts.
4. financial-safety reviewer: check advisory-only behavior, no live orders, no hidden broker path.
5. security/provenance reviewer: check secrets, paid-report handling, source hashes, ignored private files.

Wait for all agents, then summarize findings with file references and fix HIGH/CRITICAL issues.
```

Use worker subagents only when write scopes are disjoint:

```text
Spawn parallel workers:
- Worker A owns contracts/schemas only.
- Worker B owns tests/test_architecture_policy.py only.
- Worker C owns config/model_profiles.yaml and validation tests only.

Do not modify each other's files. Report changed paths.
```

## Phase Build Loop

For every phase:

1. Read `AGENTS.md` and the relevant `docs/specs`.
2. Implement only the current phase.
3. Start with failing tests.
4. Make the implementation pass.
5. Run unit and architecture policy tests.
6. Run relevant integration or evaluation checks.
7. Use parallel review subagents.
8. Fix HIGH/CRITICAL findings.
9. Report spec clauses satisfied, files changed, tests run, and remaining gaps.

## Implementation Order

Build in narrow phases:

0. Governance scaffold.
1. Contracts and schemas.
2. Data spine.
3. Model router and ModelRun ledger.
4. Deterministic signals and portfolio.
5. Evidence ingestion and provenance.
6. Recommendation artifacts and audit.
7. Evaluation harness.
8. Local read-only UI.

Do not start with UI or agents. Start with contracts plus tests so the implementation path is narrow and enforceable.

### Phase 4: Deterministic Signals And Portfolio

Implement deterministic modules for:

- Strategic thesis score
- Tactical technical score
- Forward indicator score
- Portfolio risk score
- Constraint validation
- Target-weight generation
- Recommendation-versus-trade comparison

LLM clients must not be imported or called from these modules.

### Phase 5: Evidence Ingestion And Provenance

Implement deterministic ingestion for:

- source adapters
- deterministic parsing
- content hashing
- chunking
- local embedding generation
- evidence claim extraction route
- provenance and license handling
- private report local-only defaults

LLMs may classify, extract claims, summarize, review, and explain, but all outputs must become auditable evidence artifacts.

### Phase 6: Recommendation Artifacts And Audit

Implement recommendation generation as:

1. deterministic scores
2. deterministic target weights
3. deterministic constraint validation
4. LLM-generated explanation
5. adversarial review
6. final schema validation
7. audit persistence

Every recommendation must be advisory-only and must reference evidence IDs, model run IDs, signal bundle ID, and target weights ID.

### Phase 7: Evaluation Harness

Create model and strategy evaluation cases:

- 10 SemiAnalysis-style reports
- 10 earnings/news events
- 10 portfolio recommendation cases
- 10 backtest/report-generation cases
- walk-forward split checks
- lookahead-bias checks
- recursive indicator checks
- purged CV and embargo checks
- Monte Carlo stress
- transaction cost / liquidity / slippage / capacity checks
- benchmark comparison
- shadow-mode model evaluation

Score models on:

- schema pass rate
- citation accuracy
- numeric correctness
- contradiction detection
- latency
- cost
- final recommendation usefulness
- point-in-time correctness
- leakage controls
- transaction-cost and liquidity realism
- model approval and validation status

Run DeepSeek-V4-Flash, Kimi-K2.6, and gpt-5-mini in shadow mode for one week before finalizing routing defaults.

### Phase 8: Local Read-Only UI

Build the local control-room UI after contracts, deterministic modules, model routing, recommendation artifacts, and evaluation harness exist.

Use `everything-claude-code:frontend-patterns` for React/Next.js implementation patterns and `everything-claude-code:e2e-testing` for critical UI paths. A dedicated project-local frontend implementation skill may be added later at `.agents/skills/fund-frontend-implementation/SKILL.md`.

The UI must look modern, polished, and purpose-built for a serious trading control room. It should prioritize dense, scan-friendly layouts, clear hierarchy, restrained visual styling, responsive behavior, and accessible interaction states. It must not look like a marketing landing page.

Core views:

- Portfolio
- Trade entry
- Trade journal
- Watchlist
- Ticker detail
- Suggestions
- Technical signals
- Forward tape
- Thesis map
- Evidence library
- Agent runs
- System architecture / ops room
- Data quality
- Model registry
- Incidents
- Incident/data-quality views
- No order placement or broker execution UI
- Implementation cost
- Evaluation and backtests

System architecture / ops room requirements:

- Show a live architecture map of the trading system modules: data plane, evidence plane, signal plane, portfolio engine, model router, evaluation harness, recommendation artifacts, API, worker, storage, and UI.
- Light modules green only when their required tests and health checks pass.
- Use yellow for degraded, stale, partial, or untested modules.
- Use red for failing tests, blocked health checks, incident-frozen modules, or missing required artifacts.
- Use gray for planned but not implemented modules.
- Every module status must be backed by a real source: test result, policy check, run artifact, health check, data freshness check, or incident record.
- Clicking a module should open its latest test status, run artifacts, spec clauses, dependencies, and known gaps.
- The display should feel like a trading system ops room, not a static diagram.
