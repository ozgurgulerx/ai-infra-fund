# Deployment Harness Plan: Codex Alignment, Controls, And Test-Driven Delivery

## Purpose

Define how Codex should build the AI Infrastructure Fund Control Room without drifting from the project plans and specs.

This file is not a product deployment plan. It is the implementation harness: the operating model for Codex, skills, subagents, tests, reviews, and phase gates.

The core harness rule is:

Specs define what to build. Tests constrain what can change. Codex skills and subagents enforce repeatable workflows. No phase is complete until implementation, verification, and spec traceability are all reported.

## Non-Negotiable Rules

These rules must be repeated in `AGENTS.md` and enforced by architecture policy tests:

- No live order placement or broker execution endpoint.
- The product is advisory-only.
- LLMs may extract, summarize, classify, review, and explain.
- Deterministic code owns scores, risk, backtests, constraints, and target weights.
- Business logic must not hard-code model names.
- Model routing must use `config/model_profiles.yaml`.
- PostgreSQL + pgvector owns all v1 durable records: canonical facts, portfolio records, trade journal, evidence metadata, evidence claims, embeddings, run ledger, model runs, market snapshots, factor rows, signal bundles, target weights, recommendation artifacts, audits, backtest summaries, evaluation results, and local semantic retrieval.
- Raw PDFs, CSVs, downloaded reports, and exports live on the ignored local filesystem with metadata and hashes in PostgreSQL.
- DuckDB + Parquet is a future optional analytical scale-out path only, not a Phase 2 dependency and not a v1 dependency.
- V1 runs through Docker Compose with separate `web`, `api`, `worker`, `postgres`, and `migrate` services.
- Every recommendation must include evidence IDs, model run IDs, target weights ID, signal bundle ID, and advisory-only labeling.
- `TargetWeights` must be generated by portfolio code, not directly by an LLM.
- Cloud model calls must respect data-class routing rules.
- Private reports and secrets must never be committed.
- Any deviation from specs must be called out explicitly before implementation continues.

## Codex Working Pattern

Every implementation prompt should be phase-scoped.

Required prompt shape:

```text
Read AGENTS.md and the relevant docs/specs files.
Implement Phase N only.
Start with failing tests.
Do not implement unrelated modules.
Do not change model routing, data storage, or advisory-only policy unless the spec explicitly asks for it.
After implementation, run tests and report:
- spec clauses satisfied
- files changed
- tests run
- verification output summary
- remaining gaps
```

Avoid broad prompts such as:

```text
Implement the whole app.
Build the dashboard.
Make the trading system work.
```

Broad prompts increase scope drift and make verification weaker.

## Test-Driven Development Standard

Use TDD for each implementation slice.

Required loop:

1. Read relevant spec clauses.
2. Write or update failing tests.
3. Run the failing tests and confirm they fail for the expected reason.
4. Implement the minimal code to pass.
5. Run the targeted tests.
6. Run architecture policy tests.
7. Refactor only within scope.
8. Run the full relevant test set.
9. Summarize spec traceability.

Tests should be written before implementation for:

- contracts and schemas
- model profile validation
- model router fallback behavior
- data-class allow/deny behavior
- PostgreSQL migrations and pgvector queries
- PostgreSQL market snapshot, backtest summary, and evaluation persistence
- deterministic scoring formulas
- target-weight generation
- recommendation artifact validation
- evaluation harness checks
- UI acceptance flows

## Architecture Policy Tests

`tests/test_architecture_policy.py` should verify:

- no broker execution or live order endpoint exists
- no route/path/module exposes order placement
- signal modules do not import LLM clients
- portfolio modules do not import LLM clients
- backtest modules do not call live data endpoints during point-in-time evaluation
- model names only appear in `config/model_profiles.yaml` and tests
- recommendation artifacts require advisory labels
- recommendation artifacts require evidence IDs
- recommendation artifacts require model run IDs
- recommendation artifacts require signal bundle IDs
- recommendation artifacts require target weights IDs
- `TargetWeights` are generated only by deterministic portfolio code
- PostgreSQL owns canonical facts and audit state
- PostgreSQL owns v1 market snapshots, derived analytics, backtest summaries, and evaluation results
- no DuckDB/Parquet dependency is required for v1
- private report directories are ignored
- secrets are not committed

## Subagent Review Pattern

Use subagents for independent review after a phase implementation.

Prompt pattern:

```text
After implementing this phase, use parallel subagents:

1. spec-trace reviewer:
   Verify the diff against AGENTS.md and relevant docs/specs.

2. test-gap reviewer:
   Find missing unit, integration, policy, evaluation, and E2E tests.

3. architecture-policy reviewer:
   Check deterministic/LLM boundary, model-name hardcoding, storage ownership, and artifact contracts.

4. financial-safety reviewer:
   Check advisory-only behavior, no live orders, no broker path, and recommendation labeling.

5. security/provenance reviewer:
   Check secrets, paid-report handling, source hashes, data-class routing, and ignored private files.

Wait for all subagents, summarize findings with file references, and fix CRITICAL/HIGH issues before final response.
```

Use worker subagents only when write scopes are disjoint.

Safe worker split examples:

- contracts/schemas worker
- architecture policy tests worker
- model profile config worker
- PostgreSQL migration worker
- PostgreSQL data-persistence worker
- UI read-only dashboard worker

Do not let parallel workers edit the same files.

## Verification Report Format

Every phase closeout should report:

```text
Phase:
Spec files read:
Files changed:
Spec clauses satisfied:
Tests added:
Tests run:
Verification results:
Subagent findings:
Fixed findings:
Remaining gaps:
Known risks:
```

Do not mark a phase complete if:

- tests were not run
- architecture policy tests fail
- specs conflict
- target weights can be created by LLM output
- order/broker execution exists
- private data can be sent to cloud models without policy approval
- recommendation artifacts lack evidence/model/audit links

## Failure Handling

If a test fails:

1. Read the failure carefully.
2. Determine whether the test or implementation is wrong.
3. Fix implementation unless the test contradicts the spec.
4. If the spec is ambiguous, stop and report the ambiguity.
5. Rerun the failing test.
6. Rerun architecture policy tests if the change touches boundaries.

If a model call fails:

1. Record `ModelRun` failure metadata.
2. Use fallback chain if data-class policy allows it.
3. If all LLMs fail, continue deterministic scoring where possible.
4. Mark explanation/review unavailable rather than blocking deterministic outputs.
5. Never invent evidence to fill missing model output.

If data provenance is missing:

1. Reject the evidence item.
2. Do not create claims from it.
3. Do not use it in recommendations.
4. Log the rejection reason.

## Non-Goals

- Do not rely on Codex instructions alone for safety.
- Do not skip tests because the implementation is small.
- Do not allow unbounded implementation prompts.
- Do not let UI work define backend contracts.
- Do not allow LLM agents to own deterministic scores or weights.
- Do not treat cloud model quality as a substitute for evidence, tests, or backtests.
